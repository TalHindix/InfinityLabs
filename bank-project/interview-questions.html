1. 10-Minute Presentation Script

Tip: Speak naturally — these are talking points, not a script to memorize. Aim for confident, conversational delivery. Adjust timing based on interviewer reactions.
0:00 – 0:45 · Hook & Problem

Opening — What Problem Does This Solve?

"I built Dubai Bank — a full-stack web banking application. The goal was to simulate a real financial platform that handles the core operations users expect from a bank: checking balances, transferring money, reviewing transaction history — but with a modern twist: an AI assistant you can talk to instead of navigating menus."

"The problem I wanted to solve was: can you build a banking experience that is both secure enough to protect real financial data and simple enough that a user can just type 'send 200 AED to john@example.com' and have it happen instantly?"

0:45 – 2:00 · Tech Stack

Tech Stack

"On the frontend I used React 19 with TypeScript, built with Vite. For UI components I used Material UI, and for real-time communication Socket.IO client. Routing is handled by React Router.

On the backend, Node.js with Express 5 using ES modules. The database is MongoDB with Mongoose. Authentication uses JWT stored in httpOnly cookies. For the AI chatbot I integrated OpenAI's GPT-4o-mini with function calling. Real-time chat uses Socket.IO on both sides. Email notifications go through Brevo's SMTP API via Nodemailer. And the whole thing is containerized with Docker Compose."

"For testing I have Jest and Supertest on the backend with mongodb-memory-server for integration tests, and Vitest with React Testing Library on the frontend."

2:00 – 3:30 · Architecture

Architecture Overview

"The application follows a classic three-tier architecture: React client, Node/Express API server, and MongoDB database. The server is organized in a clean layered pattern — Routes → Controllers → Services → Models. Business logic lives in the service layer, controllers only handle HTTP concerns, and models own the schema validation."

"There are two communication channels between client and server: standard REST API over HTTP for all the banking operations, and a persistent WebSocket connection via Socket.IO exclusively for the chatbot. The WebSocket has its own JWT-based authentication middleware separate from the REST middleware."

"I deliberately kept this as a monolith — one Express server handles both REST and WebSocket. For a project at this scale that's the right call: simpler deployment, simpler debugging, no distributed transaction complexity."

3:30 – 5:30 · Key Features

Key Features

"Authentication: Users sign up, receive a verification email with a token, verify their email before they can log in. Login issues a JWT valid for 1 hour stored as an httpOnly cookie — so it's not accessible from JavaScript, protecting against XSS. The verification token itself is hashed with SHA-256 before storing in the database, so even a database breach doesn't expose valid tokens."

"Money Transfers: This is the most critical part. Every transfer runs inside a MongoDB session transaction — so either both the deduction from sender and credit to receiver happen, or neither does. The balance check is an atomic MongoDB operation using a conditional update: I filter by balance >= amount, so if the check and deduct aren't atomic, the transfer fails. There's no TOCTOU race condition."

"AI Chatbot: The chatbot uses GPT-4o-mini with function calling — I defined four tools: get balance, get transaction history, transfer money, and list services. The model decides which tools to call based on what the user says. I implemented a tool-call loop that handles multi-step reasoning — the model can call a tool, see the result, then call another. Transfers through the chatbot go through the same ACID transaction service as the REST API."

"Video Calling: After a transfer, the sender can notify the recipient with an email that includes a Jitsi video call link. The room name is a SHA-256 hash of both emails sorted alphabetically — so it's deterministic, the same two users always get the same room."

5:30 – 7:30 · Interesting Technical Decisions

Interesting Technical Decisions

"Two different ID strategies: Users get a UUID from crypto.randomUUID() — non-sequential, privacy-preserving, can't enumerate users by ID. Transactions get auto-incrementing sequential IDs from a MongoDB Counter document — easier for users to reference, easier to audit."

"Chatbot state in memory, not database: Each Socket.IO connection holds the last 20 messages in socket.data.chatHistory. When the socket disconnects, history is gone. This is intentional — it keeps the system stateless at the database level for the chatbot, avoids a whole storage design problem, and honestly matches how users use chat: session-based."

"Rate limiting at multiple layers: The REST API uses express-rate-limit — stricter on auth endpoints (5 requests per 15 minutes) to prevent brute force. The chatbot has its own in-memory rate limiter — a Map of userId to count and reset timestamp — 10 messages per 60 seconds, because WebSocket connections bypass express-rate-limit."

"Async email delivery: Emails are fire-and-forget. The signup response doesn't wait for the email to send. This keeps API response times fast and prevents email provider outages from breaking signups. Failures are logged via Winston but don't surface to the user."

7:30 – 9:00 · Challenges & What I Learned

Challenges

"The hardest part was the OpenAI function calling loop. The model sometimes chains multiple tool calls — it checks the balance, then decides to transfer. I had to implement a loop with a max-rounds guard (5 rounds) to prevent infinite API calls. Also, input sanitization on the chatbot had to happen server-side — the client can send arbitrary strings, so I strip HTML tags, enforce a 250-character limit, and trim whitespace before any of it reaches OpenAI."

"Another challenge was authenticating Socket.IO. The standard Express JWT middleware doesn't apply to WebSocket handshakes, so I wrote a separate authenticateSocket middleware that extracts the token from the handshake auth object or the cookie header, verifies it, looks up the user, and attaches them to socket.data."

9:00 – 10:00 · Close

Closing

"Overall, I'm proud of this project because it touches almost every layer of modern web development: secure authentication, ACID-compliant financial transactions, real-time WebSocket communication, AI integration with tool use, email delivery, Docker containerization, and a full test suite."

"I'd be happy to go deeper on any part — the transaction atomicity, the OpenAI integration, the security model, or any architecture decisions."

2. System Flows — High Level & Low Level

Authentication Flow

High Level

  1. Client User fills signup form → POST /api/v1/auth/signup
  2. Server Validates input, hashes password with bcrypt (10 rounds), creates User with status=PENDING, generates verification token, stores its SHA-256 hash
  3. Email Sends verification email async (Brevo SMTP) with plaintext token in URL
  4. Client User clicks link → GET /api/v1/auth/verify?token=XYZ
  5. Server Hashes the received token, finds matching user, sets status=ACTIVE, clears token field
  6. Client User logs in → POST /api/v1/auth/login
  7. Server Looks up user by email, bcrypt.compare(), if active: signs JWT, sets httpOnly cookie
  8. Client All subsequent requests send cookie automatically; 401 responses trigger automatic redirect to login

Low Level Implementation Details

// jwt.util.js — token creation export const createToken = (user) => { return jwt.sign( { id: user.id, email: user.email }, // payload: UUID + email only config.jwt.secret, { expiresIn: '1h' } ); }; // Cookie set in auth.controller.js res.cookie('token', token, { httpOnly: true, // not accessible via JS → blocks XSS theft secure: isProduction, // HTTPS only in prod sameSite: 'lax', // CSRF protection maxAge: 3600000 // 1 hour in ms }); // Verification token: never stored as plaintext const rawToken = crypto.randomBytes(32).toString('hex'); const hashedToken = crypto.createHash('sha256').update(rawToken).digest('hex'); // rawToken goes in email URL, hashedToken stored in DB // Auth middleware — extracts token from cookie OR Bearer header const token = req.cookies?.token ?? req.headers.authorization?.replace('Bearer ', '');

Money Transfer Flow

High Level

  1. Client User fills transfer form → POST /api/v1/transactions (with JWT cookie)
  2. Middleware JWT verified, user attached to req.user; rate limiter checked (10/min)
  3. Controller Validates: amount in range 0.01–1,000,000 AED, max 2 decimals, not self-transfer
  4. Service Opens MongoDB session, starts transaction
  5. DB Atomic deduct from sender (conditional on balance >= amount)
  6. DB Add amount to receiver; increment Counter for sequential transaction ID
  7. DB Create Transaction document; commit session
  8. Server Returns transaction object; client optionally triggers email notification

Low Level Implementation Details

// transaction.service.js — ACID transfer export async function executeTransfer(senderEmail, receiverEmail, amount, description) { const session = await mongoose.startSession(); session.startTransaction(); try { // Step 1: Atomic deduct — only succeeds if balance >= amount const sender = await User.findOneAndUpdate( { email: senderEmail, balance: { $gte: amount } }, // ← atomic check+deduct { $inc: { balance: -amount } }, { session, new: true } ); if (!sender) throw new AppError('Insufficient balance', 400); // Step 2: Credit receiver const receiver = await User.findOneAndUpdate( { email: receiverEmail }, { $inc: { balance: amount } }, { session } ); if (!receiver) throw new AppError('Receiver not found', 404); // Step 3: Sequential ID + record const txnId = await getNextTransactionId(session); const [transaction] = await Transaction.create([ { id: txnId, fromEmail: senderEmail, toEmail: receiverEmail, amount, description } ], { session }); await session.commitTransaction(); return transaction; } catch (error) { await session.abortTransaction(); // ← full rollback throw error; } finally { session.endSession(); } } // Counter — atomic sequential ID (no race condition) const counter = await Counter.findByIdAndUpdate( 'transactions', { $inc: { seq: 1 } }, { new: true, upsert: true, session } );

AI Chatbot Flow

High Level

  1. Client User opens chat widget → Socket.IO connection established with JWT in handshake
  2. Server Socket auth middleware verifies JWT, attaches user to socket.data
  3. Client User types message → socket.emit('user-message', text)
  4. Server Rate limit checked (10 msg/min). Input sanitized (250 chars, HTML stripped)
  5. OpenAI Messages array (system prompt + chat history + new message) sent to GPT-4o-mini with 4 tool definitions
  6. Server If model returns tool_calls: execute tools (balance/history/transfer), feed results back to OpenAI — repeat up to 5 rounds
  7. Server Final text response emitted back via socket.emit('bot-message', {...})
  8. Server If transfer executed: also emit 'transfer-completed' event so UI updates balance

Low Level Implementation Details

// Socket auth middleware (socketAuth.middleware.js) export const authenticateSocket = async (socket, next) => { const token = socket.handshake.auth?.token ?? getTokenFromCookie(socket.handshake.headers.cookie); const decoded = verifyToken(token); // throws if expired/invalid socket.data.user = await findActiveUserById(decoded.id); next(); }; // In-memory rate limiter for WebSocket (socket.handler.js) const rateLimitMap = new Map(); // userId → { count, resetAt } const isRateLimited = (userId) => { const now = Date.now(); const entry = rateLimitMap.get(userId) ?? { count: 0, resetAt: now + 60000 }; if (now > entry.resetAt) entry = { count: 0, resetAt: now + 60000 }; if (entry.count >= 10) return true; entry.count++; rateLimitMap.set(userId, entry); return false; }; // Tool call loop (openaiFunctionCall.service.js) let response = await callOpenAI(messages, tools); let rounds = 0; while (response.tool_calls?.length > 0 && rounds < 5) { rounds++; messages.push(response); // assistant turn const results = await processAllToolCalls(response.tool_calls, userId); messages.push(...results); // tool result turns response = await callOpenAI(messages, tools); // next OpenAI call } // Chat history stored per socket connection (not DB) socket.data.chatHistory = []; // max 20 entries, cleared on disconnect

Full Request Flow: Frontend → Backend → Database

Example: GET /api/v1/me (Dashboard Load)

  1. React DashboardPage mounts → useDashboardData hook calls userService.getProfile()
  2. Axios http-client.ts sends GET /api/v1/me with withCredentials:true (cookie sent automatically)
  3. Express Request hits protect middleware → extracts token from cookie → verifyToken() → DB lookup for user
  4. Express Route handler calls user.controller.js → getMe() → userService.getAccountSummary()
  5. MongoDB User.findOne({ id }) + Transaction.find({$or:[fromEmail,toEmail]}).sort().limit(10)
  6. Express Returns { success: true, data: { user, transactions } }
  7. Axios Response → React state update → component re-renders with data
  8. Axios Interceptor If response is 401 → clears auth state → redirects to /login

3. Architecture & Design

Q1Medium

Why did you build this as a monolith instead of microservices?

What the interviewer is testing

Whether you understand trade-offs, not just that microservices exist.

Strong answer

  • Microservices add operational complexity: service discovery, inter-service auth, distributed tracing, network latency between calls.
  • For this project's scale — one team, one deploy — a monolith is faster to build, easier to debug, simpler to deploy with Docker Compose.
  • The money transfer requires atomicity across user and transaction data. In a monolith, one DB session handles it. In microservices you'd need distributed transactions (2PC or saga pattern) — far more complexity for no gain here.
  • You can always extract services later if you have clear domain boundaries and load demands. Premature decomposition is the bigger risk.
Q2Medium

Why MongoDB over a relational database like PostgreSQL for a banking app?

What the interviewer is testing

Honest trade-off analysis — there's no perfect answer, but you must show you know the downsides.

Strong answer

  • MongoDB 4+ supports multi-document ACID transactions, which I use for money transfers — so the "MongoDB can't do transactions" objection doesn't apply here.
  • The document model fits: a user has a profile + balance in one document, transactions are their own collection. No complex joins needed for the read paths.
  • Flexible schema was useful during development — I could evolve the model without migrations.
  • Honest trade-offs: SQL's relational integrity (foreign keys) would catch data inconsistencies at the DB level that Mongoose schema validation doesn't. For a production bank, I'd seriously evaluate PostgreSQL — its ecosystem for financial data (row-level locking, SERIALIZABLE isolation, triggers) is more mature.
  • For this project, MongoDB was a reasonable choice given the learning goals and transaction support.
Q3Hard

How would you scale this application to handle 100,000 concurrent users?

What the interviewer is testing

Scalability thinking — statelessness, load balancing, bottlenecks.

Strong answer

  • Stateless REST: The REST server is stateless (JWT in cookie, no server-side session) — I can horizontally scale it behind a load balancer immediately.
  • Socket.IO bottleneck: The chatbot rate limiter uses in-memory Map — this breaks with multiple server instances. Solution: move rate limit state to Redis (or use Redis adapter for Socket.IO to synchronize WebSocket events across instances).
  • Chat history: Currently in socket.data — fine per instance, but users would lose history if their connection moves to a different instance. Could store in Redis with TTL.
  • Database: MongoDB replica set for read replicas; shard if write volume grows. Add indexes I already have on (fromEmail, createdAt) and (toEmail, createdAt).
  • OpenAI calls: These are synchronous in the chatbot — under load, consider a queue (BullMQ + Redis) so chatbot messages are processed async and don't block event loop.
  • CDN: Static React build behind CDN — reduces server load for frontend assets.
Q4Medium

Walk me through how you'd find the top 10 richest users in your database efficiently.

What the interviewer is testing

MongoDB query knowledge, indexes, aggregation.

Strong answer

  • Simple approach: User.find({}).sort({ balance: -1 }).limit(10).select('firstName lastName balance email')
  • For this to be efficient at scale, I need an index on balance: userSchema.index({ balance: -1 }). Without it, MongoDB does a full collection scan.
  • The current schema doesn't have this index — I'd add it if this became a real query.
  • If I needed more stats (total transferred, account age), I'd use the aggregation pipeline with $lookup to join transaction data.
  • Alternatively, a materialized view updated by a background job could pre-compute a leaderboard if this is read-heavy.
Q5Easy

Why do you use two different ID strategies — UUID for users and sequential integers for transactions?

What the interviewer is testing

Thoughtfulness about ID design choices.

Strong answer

  • User UUIDs: Non-sequential, can't be enumerated. If a user's ID appears in a URL or token, an attacker can't guess other user IDs by incrementing. Privacy-preserving.
  • Transaction sequential IDs: Users reference transactions by number ("Transaction #247"). Sequential IDs are human-readable, easy to find in support conversations, and easy to audit in order. A UUID like a8f3c2... is useless to a customer service rep.
  • The counter is implemented as an atomic MongoDB findByIdAndUpdate with $inc — guaranteed unique, no race conditions, no gaps (well, minor gaps possible on rollback — acceptable for this use case).
Q6Medium

How does your layered architecture (Routes → Controllers → Services → Models) benefit the project?

What the interviewer is testing

Understanding of separation of concerns and maintainability.

Strong answer

  • Controllers only handle HTTP: extract params, call services, send response. No business logic.
  • Services contain all business logic (transfer rules, balance checks, OpenAI calls). They're testable without HTTP.
  • Models own schema and DB-level validation. Nothing else talks to MongoDB directly.
  • This means: I can test executeTransfer() directly without spinning up Express. I can swap the HTTP layer for GraphQL without touching services. I can mock services in controller tests.
  • In practice: my integration tests call the service functions directly with a real in-memory MongoDB, which is both fast and accurate.
Q7Hard

What happens if the server crashes between committing the MongoDB transaction and sending the HTTP response?

What the interviewer is testing

Distributed systems edge cases — you won't always know the answer, but showing you've thought about it matters.

Strong answer

  • The transaction is committed to MongoDB — the money has moved. But the client gets a network error and doesn't know.
  • This is the "at-least-once delivery" problem. The client might retry the transfer, causing a double transfer.
  • Mitigation: idempotency keys. The client sends a unique request ID; the server checks if this ID was already processed before executing. If yes, return the cached result without re-running.
  • My current implementation doesn't handle this — it's a known limitation I'd address in production. For now, the transaction history lets users verify whether a transfer went through.
  • This is why real payment systems (Stripe) are built around idempotency keys at the API level.
Q8Medium

How does your frontend handle authentication state and protect routes?

What the interviewer is testing

Frontend auth patterns — cookies vs localStorage, route guards.

Strong answer

  • The JWT lives in an httpOnly cookie — the React app can't read it. So auth state is inferred: a flag stored in localStorage (or a React context) tracks whether the user is logged in.
  • The custom useAuth hook manages this state. On startup it checks localStorage for the auth flag, makes a GET /api/v1/me call to verify with the server, and sets the context accordingly.
  • Protected routes in App.tsx render a redirect to /login if the user isn't authenticated.
  • The Axios http-client has a response interceptor: any 401 response clears the auth state and redirects to login — handles token expiry gracefully without the user seeing an error.
  • auth.storage.ts uses localStorage events so multiple tabs stay in sync when one tab logs out.
Q9Easy

Why did you use Docker Compose?

What the interviewer is testing

DevOps basics and environment reproducibility.

Strong answer

  • Docker Compose lets me define both the Node server and MongoDB as services with one file. A single docker compose up starts everything.
  • Eliminates "works on my machine" — the environment is defined in code (image versions, env vars, networking).
  • For local development, I can swap the MongoDB container for a cloud Atlas instance just by changing the connection string in an env var.
  • For CI/CD, the same compose file can be used to spin up a test environment.
Q10Medium

What is your testing strategy and what are you testing vs not testing?

What the interviewer is testing

Understanding of test pyramids and pragmatic testing choices.

Strong answer

  • Unit tests: JWT utility functions, validation logic — pure functions, fast, no dependencies.
  • Integration tests: Auth routes and transaction flow using Supertest + mongodb-memory-server. These test the full request pipeline without mocking the DB — I get real query behavior.
  • Frontend tests: Custom hooks (useAuth, useTransfer) with React Testing Library, API service layer with mocked Axios.
  • Not tested: Email delivery (would need SMTP mock), OpenAI calls (mocked at service boundary), the UI visually.
  • The mongodb-memory-server approach is better than mocking — it catches real query issues, index behavior, and Mongoose validation that mocks would hide.

4. Backend — Node.js, Express, APIs

Q11Medium

How did you prevent brute-force attacks on the login endpoint?

What the interviewer is testing

Security awareness, rate limiting implementation.

Strong answer

  • express-rate-limit middleware on auth endpoints: 5 requests per 15 minutes per IP on /login, /signup, and /resend-verification.
  • After 5 failed attempts, the endpoint returns 429 Too Many Requests.
  • bcrypt's deliberate slowness (10 salt rounds, ~100ms per comparison) also limits brute force speed — an attacker can't test thousands of passwords per second even if rate limiting is bypassed.
  • The verification token is SHA-256 hashed in storage — even if the DB is compromised, an attacker can't use stored tokens to verify accounts.
  • Improvement: account lockout after N failures, or CAPTCHA for repeated failures.
Q12Easy

What is the difference between PUT and PATCH? Which would you use for updating a user profile?

What the interviewer is testing

REST semantics knowledge.

Strong answer

  • PUT replaces the entire resource — you send the full object, missing fields are cleared.
  • PATCH partially updates — you send only the fields you want to change.
  • For profile updates, PATCH is correct. You might only want to update firstName — sending PUT would require including every other field or risk clearing them.
  • In my project, there's currently no profile update endpoint — but if I added one, I'd use PATCH with explicit whitelisting of updatable fields (firstName, lastName, phone) to prevent mass assignment attacks.
Q13Medium

Why did you use ES modules (import/export) instead of CommonJS (require) in Node.js?

What the interviewer is testing

Awareness of Node.js module systems.

Strong answer

  • ES modules are the standard — they work the same in browser and Node, which reduces cognitive overhead.
  • Static imports enable tree-shaking (relevant for bundlers) and better static analysis.
  • ES modules are always strict mode — catches common bugs.
  • Trade-off: some older npm packages are CJS-only, which can cause interop headaches (the "ERR_REQUIRE_ESM" problem). I configured package.json with "type": "module" to opt in.
  • For new projects in Node 18+, ES modules are the right default.
Q14Medium

How does your centralized error handling middleware work?

What the interviewer is testing

Express middleware patterns, error propagation.

Strong answer

  • Express error middleware has four parameters: (err, req, res, next). It must be registered after all routes.
  • I defined a custom AppError class with a statusCode and isOperational flag. Operational errors (bad input, not found) get their message sent to the client. Programmer errors (bugs) get a generic "Internal server error" message — don't leak stack traces.
  • All async route handlers call next(err) on failure — or use a wrapper that catches thrown errors automatically.
  • The error middleware logs every error via Winston, maps MongoDB errors (duplicate key → 409, validation → 400), and sends a consistent { success: false, error: "..." } JSON response.
  • This means no try/catch in route handlers — cleaner code, consistent error format.
Q15Medium

What's the difference between authentication and authorization? How do you implement both?

What the interviewer is testing

Security fundamentals.

Strong answer

  • Authentication: Who are you? Verified via JWT. My protect middleware decodes the token, looks up the user in the DB (checks they're still ACTIVE), and attaches them to req.user.
  • Authorization: Are you allowed to do this? In my app, all authenticated users can transfer. But authorization is implicit: GET /api/v1/me uses req.user.id — a user can only see their own data. GET /api/v1/transactions filters by req.user.email — you can only see your own transactions.
  • There's no role-based access control (RBAC) currently. An admin role would be a natural addition — but I didn't add it since there's no admin functionality.
Q16Easy

What is CORS and how did you configure it?

What the interviewer is testing

Basic web security knowledge.

Strong answer

  • CORS (Cross-Origin Resource Sharing) is a browser security mechanism that blocks JavaScript from making requests to a different origin (domain/port) than the page it's on.
  • My frontend (localhost:5173 in dev) talks to the backend (localhost:3000) — different ports, different origins — so CORS must be configured.
  • I configured the CORS middleware to allow the specific frontend origin, allow credentials (needed for cookies), and specify allowed methods and headers.
  • Using origin: '*' with credentials is not allowed by browsers — you must specify the exact origin when cookies are involved.
  • In production, the allowed origin is set via environment variable to match the real frontend domain.
Q17Medium

Why did you make email delivery asynchronous (fire and forget)?

What the interviewer is testing

Performance vs reliability trade-offs.

Strong answer

  • The signup HTTP response doesn't wait for the email to send. This keeps the API fast — SMTP calls can take 1–3 seconds.
  • More importantly, if Brevo is down, signups still work. The user might not get the verification email immediately, but they can request a resend — we don't fail the whole operation.
  • Trade-off: if the server crashes after signup but before the email sends, the user never gets the verification email. They'd need to use resend-verification.
  • For production, a proper solution is a message queue (Redis + BullMQ) — email jobs are persisted and retried on failure, with backoff, without coupling to the HTTP request.
Q18Hard

How does the Axios 401 interceptor work on the frontend and why is it useful?

What the interviewer is testing

Frontend HTTP client patterns, token expiry handling.

Strong answer

  • Axios interceptors are middleware for HTTP requests/responses. I registered a response interceptor that runs after every API call.
  • If the response status is 401 (Unauthorized — which happens when the JWT expires after 1 hour), the interceptor clears the auth state in localStorage and redirects the user to /login.
  • Without this: the user would get an error screen on every API call after token expiry. With it: they're smoothly redirected to login with no visible error.
  • This is cleaner than checking for 401 in every service function individually — one place handles it for all API calls.
  • Enhancement: implement refresh tokens so the interceptor silently gets a new access token instead of redirecting — better UX.
Q19Easy

What HTTP status codes do you return and when?

What the interviewer is testing

REST best practices.

Strong answer

  • 200: Successful GET or POST that returns data
  • 201: Resource created (signup, new transaction)
  • 400: Bad request — validation failed, amount out of range, missing fields
  • 401: Authentication failed — no token, expired token, invalid token
  • 403: Forbidden — authenticated but not allowed (e.g., self-transfer blocked)
  • 404: Resource not found — receiver email doesn't exist
  • 409: Conflict — email already registered
  • 429: Too Many Requests — rate limited
  • 500: Internal Server Error — unexpected exceptions (never expose stack traces)
Q20Medium

How does transaction pagination work and how do your database indexes support it?

What the interviewer is testing

Pagination patterns, index usage.

Strong answer

  • I use offset-based pagination: GET /api/v1/transactions?page=1&limit=10. The query does .skip((page-1)*limit).limit(limit).
  • Transactions are filtered by the user's email: { $or: [{ fromEmail }, { toEmail }] } and sorted by createdAt: -1.
  • I have compound indexes on (fromEmail, createdAt) and (toEmail, createdAt) — these make this query efficient. MongoDB can satisfy both the filter and sort from the index without a full collection scan.
  • Limitation of offset pagination: if transactions are added while the user pages through results, they might see duplicates or miss entries. Cursor-based pagination (using the last seen ID as the starting point) solves this — better for real-time data.
  • Max page size is capped at 100 to prevent abusive large queries.

5. Database — MongoDB & Transactions

Q21Hard

Explain exactly how your money transfer is ACID-compliant. What does each letter mean in your context?

What the interviewer is testing

Deep understanding of database transactions, not just that you used them.

Strong answer

  • Atomicity: All three operations (deduct sender, credit receiver, create record) happen together or not at all. If any fails, abortTransaction() rolls back all changes. Money can't disappear in the middle.
  • Consistency: The balance field has a min: 0 constraint. The conditional update balance: { $gte: amount } ensures we never go below zero. Schema validation catches invalid amounts before they reach the DB.
  • Isolation: MongoDB sessions with multi-document transactions provide snapshot isolation — concurrent transfers see a consistent view of balances and don't interfere.
  • Durability: MongoDB's default write concern ensures committed transactions are persisted to disk before reporting success. Even if the server crashes after commit, the data survives.
Q22Hard

Could two concurrent transfers from the same account cause the balance to go negative? Why or why not?

What the interviewer is testing

Race condition understanding, atomic operations.

Strong answer

  • No — and here's why. The deduct operation is a single atomic MongoDB command: findOneAndUpdate({ email, balance: { $gte: amount } }, { $inc: { balance: -amount } }).
  • The filter and the update happen atomically at the database level. Two concurrent transfers both race to this operation. Only one can see balance >= amount true and apply the decrement first. The second then sees the reduced balance — if it's now insufficient, the filter fails, the update doesn't execute, and the transfer aborts.
  • The MongoDB session transaction wraps all three operations — so the isolation level ensures concurrent transactions don't see each other's partial state.
  • The key insight: I'm not doing read → check → write separately (which would have a TOCTOU race). I'm doing conditional write — the check and the write are one atomic database operation.
Q23Medium

Why did you use a Counter document for transaction IDs instead of MongoDB's default ObjectId?

What the interviewer is testing

Understanding of ID design trade-offs.

Strong answer

  • ObjectId is a 24-character hex string (e.g., 64f2b3c9a7e1c2d3e4f5a6b7) — not human-friendly for references.
  • Sequential integers (e.g., Transaction #247) are easy for users to reference, easy for support teams to look up, and easy to verify ordering.
  • Implementation: a Counter document with findByIdAndUpdate($inc) is an atomic MongoDB operation — guaranteed no two transactions get the same ID, even under concurrent writes.
  • Caveat: if a transaction is rolled back, the counter still incremented — you'll have gaps in the sequence. That's acceptable; the IDs are still unique and ordered. A zero-gap sequence would require holding the counter increment inside the same transaction and rolling it back on failure, which would require the counter to be part of the session.
  • In my implementation, the counter IS inside the session — so gaps would only occur on abort, which is the correct behavior.

How would you calculate the total volume of money transferred through the system?

Q26Easy

How does bcrypt password hashing work and why not use SHA-256?

What the interviewer is testing

Password security fundamentals.

Strong answer

  • bcrypt automatically generates a random salt (incorporated into the hash) and runs a configurable number of hashing rounds. I use 10 rounds — takes ~100ms per hash.
  • SHA-256 is fast by design — a GPU can compute billions per second. That makes it terrible for passwords: attackers can brute-force a leaked database quickly.
  • bcrypt is slow by design. 10 rounds means ~100ms per attempt. An attacker trying a million passwords takes 100,000 seconds instead of milliseconds.
  • The salt prevents rainbow table attacks — two users with the same password get different hashes.
  • bcrypt's work factor (rounds) can be increased over time as hardware gets faster — no need to rehash all passwords, just increase the factor for new logins.
  • I use SHA-256 for the verification token (not password) — that's appropriate because the token is random (64 hex chars), long, and single-use. You just need to verify a given token matches the stored hash, not protect against brute force.
Q27Medium

What is the N+1 query problem and do you have it anywhere in your project?

What the interviewer is testing

Database query efficiency awareness.

Strong answer

  • N+1: fetch N records, then make N individual queries to get related data for each — instead of one join query.
  • My app doesn't have this problem currently because I don't join across collections in user-facing queries. The dashboard fetches user + last 10 transactions in two queries — not N+1.
  • If I added a feature like "show sender's full name for each transaction in history," I could introduce it: fetch 10 transactions, then query User for each sender email = 10 extra queries. Fix: use $lookup in an aggregation pipeline, or batch all emails into one User.find({ email: { $in: emails } }).
Q28Hard

MongoDB vs PostgreSQL for a financial application — make the case for each.

What the interviewer is testing

Honest trade-off analysis without being defensive about your choice.

Strong answer

Case for MongoDB (my choice):

  • Multi-document ACID transactions supported since v4.0 — handles transfers correctly.
  • Flexible schema — faster iteration during development, no migration scripts for each model change.
  • Horizontal scaling (sharding) built in — better for write-heavy global scale.
  • Document model fits user profile + recent transactions as one fetch.

Case for PostgreSQL (stronger for production banking):

  • Foreign key constraints enforce referential integrity at the DB level — Mongoose schema validation doesn't stop orphaned transaction records.
  • SERIALIZABLE isolation level and row-level locking are more battle-tested for financial systems.
  • Richer ecosystem: triggers, stored procedures, check constraints, views.
  • JOIN queries are native and efficient — better for complex reporting (monthly statements, audit trails).
  • DECIMAL type for money — avoids floating-point precision issues. MongoDB uses double by default.
  • Bottom line: For a real bank, PostgreSQL. For this learning project, MongoDB was a valid choice given its transaction support.
Q29Medium

How does the email verification token work securely if it's sent in plaintext over email?

What the interviewer is testing

Understanding of token security and threat model.

Strong answer

  • The threat we're protecting against is a database breach — not email interception. If someone dumps the DB, they get the hashed token, not the raw one. They can't reverse SHA-256 to get the raw token.
  • The email contains the raw token. Email interception is a separate threat (mitigated by TLS in transit). If the email is intercepted, yes, the attacker can verify the account — but that requires active network attack, not just a leaked database.
  • The token is 32 random bytes = 64 hex chars — too long to brute force, single-use (cleared after verification), expires if not used (improvement I'd add: set an expiry timestamp).
  • This is the same pattern used by real systems like password reset emails — the DB never stores the raw reset token.
Q30Medium

Floating-point precision: why is 0.1 + 0.2 !== 0.3 in JavaScript and how does it affect your transfer amounts?

What the interviewer is testing

Numeric precision awareness in financial systems — a classic trap.

Strong answer

  • IEEE 754 double-precision floats can't represent all decimal fractions exactly. 0.1 + 0.2 = 0.30000000000000004 in binary.
  • For money, this can cause 1-cent errors in accumulated calculations.
  • My validation enforces max 2 decimal places with a regex on the amount. This reduces (but doesn't eliminate) floating-point issues.
  • Better production approach: store amounts as integers (cents/fils). 1,234.56 AED stored as 123456 fils. All arithmetic is integer arithmetic — no precision issues. Convert to decimal only for display.
  • MongoDB has no native DECIMAL type (unlike PostgreSQL). This is another reason PostgreSQL is preferable for financial data.
  • I'd acknowledge this as a known limitation of my current implementation.

6. Security & Auth

Q31Medium

What's the difference between XSS and CSRF? How does your app defend against each?

What the interviewer is testing

Web security fundamentals and how your specific design choices address them.

Strong answer

  • XSS (Cross-Site Scripting): Attacker injects script into your page that runs in victims' browsers. Defense: httpOnly cookie — the JWT is not accessible to JavaScript, so even if XSS runs, it can't steal the auth token. React also escapes rendered content by default.
  • CSRF (Cross-Site Request Forgery): A malicious site tricks the browser into sending authenticated requests to your API (cookies are sent automatically by the browser). Defense: sameSite: 'lax' cookie attribute — the browser won't send the cookie for cross-origin POST requests initiated by other sites. This covers the vast majority of CSRF attacks.
  • For stronger CSRF protection, add a CSRF token (double-submit cookie pattern) — but SameSite=Lax is sufficient for most modern browsers.
Q32Medium

What are the security implications of storing the JWT in a cookie vs localStorage?

What the interviewer is testing

Auth token storage trade-offs.

Strong answer

  • localStorage: Accessible to JavaScript — vulnerable to XSS theft. If any script on your page (including third-party analytics) is compromised, the token is stolen. Not sent automatically — must manually add Authorization header, which is actually CSRF-safe but requires more frontend code.
  • httpOnly Cookie: Not accessible to JavaScript — XSS can't steal it. Sent automatically by the browser — need CSRF protection (SameSite). My choice.
  • Memory (JS variable): Safest against XSS and CSRF — but lost on page refresh, requires refresh token flow.
  • My choice (httpOnly cookie with SameSite:lax) is the current industry best practice for traditional web apps — it defeats both XSS token theft and CSRF in one.
Q33Hard

How would you implement refresh tokens to extend session without re-login?

What the interviewer is testing

Token lifecycle management — a common production requirement.

Strong answer

  • Issue two tokens on login: access token (15min, in-memory or short-lived cookie) and refresh token (7 days, httpOnly cookie, stored hash in DB).
  • When the access token expires, the client (or Axios interceptor) calls POST /api/v1/auth/refresh with the refresh token cookie.
  • Server validates the refresh token hash in DB, issues a new access token, optionally rotates the refresh token (old one invalidated).
  • On logout, delete the refresh token from DB — even if someone has the old refresh cookie, it's invalidated.
  • This allows token revocation (not possible with stateless JWTs alone), shorter access token lifetime (reduces exposure window), and seamless UX.
  • Current app: 1-hour JWT, redirect to login on expiry. Adding refresh tokens is the natural next step.
Q34Medium

How do you prevent SQL injection — and does that apply to MongoDB?

What the interviewer is testing

Injection attack understanding, MongoDB-specific risks.

Strong answer

  • SQL injection doesn't apply directly to MongoDB — there's no SQL. But MongoDB has its own injection vector: NoSQL injection via query operator injection.
  • Example: if I did User.findOne({ email: req.body.email }) and the attacker sends { "email": { "$gt": "" } }, MongoDB would return the first user — bypassing authentication.
  • Defense: Mongoose schema validation rejects unexpected types. Email is a String type in the schema — if an object is passed, Mongoose throws a CastError before the query executes.
  • Additionally, I use parameterized Mongoose queries (not string concatenation), and input validation checks that email is a string and matches the email regex before it reaches the DB layer.
  • For the chatbot, server-side sanitization strips HTML and limits length — prevents prompt injection from affecting the system prompt as well.
Q35Medium

What would happen if an attacker set their transfer amount to -100 to steal money?

What the interviewer is testing

Input validation, security thinking about edge cases.

Strong answer

  • The amount validation in the validation utility enforces: must be a number, must be > 0, minimum 0.01, maximum 1,000,000, max 2 decimal places.
  • A negative amount would fail this validation and return a 400 Bad Request before reaching any database operation.
  • Additionally, the Transaction model schema has min: 0.01 on the amount field — so even if validation was bypassed somehow, Mongoose would reject it at the DB level.
  • The balance deduction uses $inc: { balance: -amount } — if amount were -100, it would be $inc: { balance: 100 } which would add to the sender's balance. But this never reaches that code path due to validation.
  • Defense in depth: multiple validation layers, not just one.

Secrets management basics.

What is the threat model for your chatbot? Could a user extract sensitive data about other users?

What the interviewer is testing

AI security thinking — prompt injection, data isolation.

Strong answer

Q38Medium

How does Socket.IO authentication work differently from REST authentication?

What the interviewer is testing

WebSocket security — a frequently missed area.

Strong answer

  • REST: every request is independent. The JWT middleware runs on every request, extracts the token, verifies it.
  • WebSocket: the connection is persistent. Authentication happens once at connection time (handshake). After that, the same user context persists for the lifetime of the connection.
  • My Socket.IO auth middleware (authenticateSocket) runs during the handshake — it checks the token in socket.handshake.auth.token or the Cookie header, verifies it, and attaches the user to socket.data.user.
  • Once connected, all messages from that socket are trusted as that user — no per-message token check needed.
  • Implication: if a JWT expires mid-session, the socket stays connected (the token was valid at connect time). The user would need to reconnect to re-authenticate. This is a known behavior — mitigation: check token expiry on each message, or use short-lived WebSocket session tokens.

Q42Medium

Why WebSockets for the chatbot instead of regular HTTP polling or Server-Sent Events?

What the interviewer is testing

Real-time communication trade-offs.

Strong answer

Q45Tricky

"Your chatbot can execute real bank transfers. Isn't that a serious security risk?"

What the interviewer is testing

Your ability to defend a non-obvious design decision calmly and with nuance.

Strong answer

  • Yes — it's a real risk, and I've thought about it. Several mitigations are in place:
  • The chatbot only has access to the authenticated user's account — it can't transfer money on behalf of other users.
  • The system prompt requires explicit confirmation before transfer execution.
  • The rate limiter (10 msg/min) limits how fast an attacker could attempt transfers.
  • Transfers through the chatbot use the identical ACID transaction service as the REST API — the same balance checks, validation, and atomicity apply.
  • Input sanitization reduces prompt injection attack surface.
  • For production, I'd add: a dedicated UI confirmation step that bypasses the LLM entirely (the LLM proposes, the UI confirms), a separate lower rate limit for chatbot-initiated transfers, and possibly two-factor confirmation for transfers above a threshold.
  • This is a genuine trade-off between user convenience and security that real fintech products (like Venmo's AI features) also have to navigate.
Q46Tricky

"Your JWT never gets invalidated until expiry. What if a user's account is compromised?"

What the interviewer is testing

Stateless JWT limitations — a real and well-known problem.

Strong answer

  • You're right — this is the fundamental trade-off of stateless JWTs. If a user's token is stolen, the attacker has access for up to 1 hour (the expiry), even if the user changes their password or we deactivate their account.
  • My auth middleware does query the database on every request to check the user is still ACTIVE — so if I set user.status = 'SUSPENDED', the token becomes invalid immediately.
  • Full solution: a token blocklist. On logout or forced invalidation, add the token's jti (unique token ID) to a Redis blocklist. The auth middleware checks this list. After expiry, the token falls off automatically (TTL matches expiry).
  • Alternative: short-lived tokens (15 min) + refresh tokens. The refresh token can be invalidated server-side, and the access token expires quickly anyway.
  • My current 1-hour expiry + status check in the DB is a reasonable middle ground for this project.
Q47Tricky

"What if two users send money to each other simultaneously — both have 100 AED and both try to send 100 AED to each other at the exact same time?"

What the interviewer is testing

Deadlock potential in concurrent transactions — a classic database concurrency puzzle.

Strong answer

  • This is a potential deadlock scenario. Transaction A locks User1, tries to lock User2. Transaction B locks User2, tries to lock User1. Classic circular wait.
  • MongoDB's transaction implementation uses optimistic concurrency and write-intent locks. When two transactions try to modify the same document, one of them will get a WriteConflict error and need to retry.
  • In my implementation, the abortTransaction() in the catch block handles this — the failed transaction is rolled back cleanly. The user would get an error and need to retry.
  • Production mitigation: retry logic with exponential backoff for WriteConflict errors. MongoDB documentation recommends this pattern explicitly.
  • Another approach: order lock acquisition consistently (always lock lower email alphabetically first) — eliminates circular wait. But this is more complex to implement and MongoDB's optimistic approach handles it acceptably.
Q48Tricky

"Your in-memory Socket.IO rate limiter works fine now — but what happens when you scale to 3 server instances?"

What the interviewer is testing

Whether you understand the hidden assumption in your current implementation.

Strong answer

  • It breaks. Each server instance has its own Map — they don't share state. A user could send 10 messages to instance A, 10 to instance B, 10 to instance C, and bypass the rate limit entirely.
  • Fix 1: Redis-based rate limiting. Replace the in-memory Map with Redis INCR + EXPIRE. All instances share the same Redis counter. INCR user:ratelimit:userId, set TTL of 60s, check count <= 10.
  • Fix 2: Redis Adapter for Socket.IO — not just for rate limiting, but to allow Socket.IO events to be broadcast across instances (needed anyway if you want to emit events to a user connected to a different instance).
  • Fix 3: Sticky sessions — the load balancer routes a user's WebSocket connection to the same server instance every time. Rate limiting works correctly, but you lose horizontal scaling benefits for that user.
  • Redis is the right production answer. I'd acknowledge this as a known scaling limitation of the current implementation.
Q49Tricky

"Why do you store the user's email in the Transaction document instead of a user ID reference? Isn't that a denormalization?"

What the interviewer is testing

Schema design thinking and whether you can defend your choices.

Strong answer

  • Yes, it's a denormalization — and intentional. Transactions store fromEmail and toEmail directly rather than user ObjectId references.
  • Reason 1: Transactions are an audit trail. They should record what happened at the time — including who was involved by their email. If a user later changes their email (hypothetically), the transaction record should still reflect the email at the time of the transfer.
  • Reason 2: Query simplicity. "Get all transactions for user@email.com" is a single index lookup with no join. With user ID references, I'd need a $lookup to get emails for display, adding complexity.
  • Trade-off: email is repeated across many transaction documents. If emails could change, this creates an update consistency problem. In practice, most systems treat email as immutable after signup — which is a business rule worth enforcing.
  • SQL analogy: this is like storing a customer name in an order record rather than just a customer ID — classic data warehousing pattern for historical accuracy.
Q50Tricky

"If you could rebuild this project from scratch, what would you do differently?"

What the interviewer is testing

Self-awareness, intellectual honesty, growth mindset. No wrong answer — but vague or defensive answers are weak.

Strong answer

  • Store money as integers (fils/cents): Avoid floating-point precision issues entirely. Convert to decimal only for display.
  • Refresh tokens from the start: Short-lived access tokens + long-lived refresh tokens gives better security and UX. Adding it later requires a migration.
  • Idempotency keys on the transfer API: Prevents accidental duplicate transfers on network retry — critical for production financial APIs.

"I wouldn't change anything" — shows no critical thinking. "I'd use microservices" — without a real reason, this sounds cargo-cult. Keep it specific and grounded in real problems you encountered or limitations you identified.
